# Wave-playbook — параллельные слои для большой генерации

Когда сервис большой (Journal: 13 команд + 5 queries + ES + проекции), строй его
волнами с **параллельными слоями** (byL) — это даёт наибольший прирост полноты и
готовности (эталон: DSv4FwQSwSAbyL 98/98).

## Принцип

- Слои Domain / DomainServices / Application / Storage / Api разрабатываются
  параллельно разными агентами по **замороженным контрактам**.
- Контракт — единый источник правды: `contracts.md` с ревизиями `R-1 … R-N`.
- Любое расхождение со контрактом — стоп, эскалация lead, а не локальное «исправление».

## Последовательность

1. **W0 — разведка.** Прочитай канвасы и `library-known-issues.md`; сделай `library-api.md`
   из реверса фактического API (XML-доки / reflection-пробник). Заморозь контракт `contracts.md` R-1.
2. **W1 — домен.** Aggregate + VO + инварианты + state machine + domain-тесты (QG-702, QG-701).
3. **W2a ∥ W2b — инфраструктура.** Command/Event Store + Rebuild ∥ Read Store + проекции.
4. **W3 — Api.** Command/Query API строго по контракту; запрет импровизации HTTP-контракта.
5. **W4 — интеграция.** lifecycle, replay, idempotency, rebuild==incremental; фактический
   прогон тестов in-process раннером (S6) и на настоящей СУБД.

## Гейты между волнами

После каждой волны: `dotnet build -warnaserror` = 0/0 и зелёные тесты. Отчёт волны для
следующей: что сделано, что заморожено в контракте, какие обходы применены (только из
реестра). Красные тесты — не гейт, а дефект постановки: возврат на волну.

## Правила

- Существующие канвасы **не перезаписывать** — это ТЗ (шаг 0). Новая информация — в
  отдельные файлы и в ревизию контракта.
- Конфликт с контрактом → стоп, эскалация lead.
- Обходы только из `library-known-issues.md`; прочее — ошибка.
